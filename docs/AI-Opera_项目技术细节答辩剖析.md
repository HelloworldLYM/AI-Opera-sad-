# AI-Opera 智能川剧变脸项目技术细节答辩剖析

本文档面向项目答辩使用，目标不是做宣传介绍，而是把项目的真实技术路线、实现机制、工程取舍和当前边界讲清楚。文档中特别区分四类状态：

- 真正实现：当前代码中已经落地，可在本地运行或通过已有接口调用。
- 工程兜底：有真实流程，但会根据设备、依赖和资源情况自动降级。
- 预留接口：后端或前端已有入口，但需要外部服务、数据或训练结果才能发挥完整能力。
- 不宜夸大：可以作为后续方向或技术规划，但答辩时不能说成已经完整实现。

## 1. 项目总体技术路线

AI-Opera 智能川剧变脸不是单纯的网页滤镜，也不是单一的大模型问答应用。它的技术路线可以概括为：

用户摄像头输入  
-> 浏览器端人脸与手部关键点识别  
-> 动作时序状态机判断变脸触发  
-> Three.js 实时三维脸谱贴合  
-> 收藏馆记录脸谱、角色、剧目和唱段  
-> 后端执行 RAG、AI Agent、媒体检索和三维生成任务  
-> 个人三维脸谱模型页面展示 OBJ/GLB/UV 资产  
-> 后续可接入 AutoDL 训练、SAM/CLIP/VLM、3DGS 等增强能力

项目的核心不是“把图片贴到视频上”，而是把川剧变脸的表演动作拆解成可计算的数据结构：人脸关键点、手部关键点、头部姿态、动作轨迹、遮挡区域、触发状态和冷却帧。再把脸谱文化拆解为角色、颜色、寓意、剧目、唱段和知识片段，由 RAG 和小谱 Agent 组织成文化解释。

当前项目最稳定、最应该重点展示的能力是：

1. 浏览器实时摄像头变脸。
2. MediaPipe FaceMesh 和 Hands 驱动的人脸、手部感知。
3. 挥手、转头回正、舞扇遮脸、侧首吐火等动作触发。
4. Three.js 三维面部网格贴图。
5. 脸谱收藏馆、角色知识和部分唱段联动。
6. 小谱 AI 导览 Agent 与 RAG 知识库。
7. 个人三维脸谱面罩展示。
8. 后端 3DDFA-V3 / fallback OBJ / mock 的三维生成链路。

当前不宜宣传成完全成熟的能力是：

1. 高保真人脸重建。
2. 本机实时 SAM 精细分割。
3. 本机完整 CLIP/VLM 多模态理解。
4. 本机完整 3D Gaussian Splatting 训练和沉浸式重建。
5. 每个角色都已接入真实经典唱段。
6. 完全自动、无需人工锚点的脸谱语义 UV 贴图。

## 2. 前端入口与双模式设计

项目的正式首页使用 Vite + React + TypeScript 构建。首页的核心作用不是直接执行变脸，而是完成项目叙事、模式选择和入口引导。

首页提供两种模式：

### 2.1 轻云入戏

轻云入戏面向首次体验和普通电脑。它的定位是“稳定优先”。在答辩中可以这样解释：

轻云模式不是低配版，而是面向普通硬件环境的稳定演示模式。它保留核心变脸、舞扇、吐火和收藏逻辑，但减少对复杂舞台氛围和大量自动入藏的依赖，让用户更容易在普通浏览器中完成第一次体验。

### 2.2 华彩入境

华彩入境面向更强性能设备和沉浸式展示。它强调更完整的舞台光影、氛围层次和展示效果。答辩中可以强调：

双模式设计解决的是设备差异问题。非遗互动展示通常要面对不同学校机房、展馆电脑、个人笔记本和浏览器环境，不能只做一个高负载版本。轻云模式保证可用性，华彩模式保证展示上限。

### 2.3 真实实现边界

真正实现的是：首页确实存在模式选择、页面跳转和 sessionStorage 模式记录。  
需要谨慎的是：目前两种模式更多是体验配置和展示路径差异，不是两套完全独立的算法系统。

## 3. 摄像头输入与浏览器实时视频流

项目的实时输入基于浏览器摄像头能力。用户点击启动摄像头后，浏览器请求权限，并通过 WebRTC 获取视频流。项目使用 MediaPipe 的 Camera 工具把摄像头帧持续送入 FaceMesh 和 Hands。

技术流程为：

1. 用户点击启动摄像头。
2. 浏览器弹出摄像头权限请求。
3. 获取 video stream。
4. 每一帧图像送入 FaceMesh。
5. 同一帧或相邻帧送入 Hands。
6. FaceMesh 返回人脸关键点。
7. Hands 返回手部关键点。
8. 渲染器和动作检测器消费这些关键点。

这里需要说明一个关键点：系统真正处理的不是原始 RGB 图像本身，而是从图像中提取出来的人脸和手部结构化关键点。这样做的优势是，后续动作识别和贴图渲染可以更多依赖几何关系，而不是依赖背景、衣服颜色、光照颜色或单帧像素。

## 4. MediaPipe FaceMesh 的作用

FaceMesh 是项目实时变脸的基础。它输出 468 个稠密人脸关键点，每个关键点包含归一化的 x、y 坐标和相对 z 深度。

项目中 FaceMesh 的作用包括：

1. 定位脸部中心。
2. 计算脸部宽高。
3. 判断用户距离摄像头的相对变化。
4. 估计头部姿态，如 yaw、pitch、roll。
5. 提供眼睛、鼻梁、嘴部、下巴、脸颊等语义区域。
6. 驱动 Three.js 面部网格的顶点更新。

答辩中可以这样讲：

FaceMesh 把摄像头中的人脸从一张二维图像转成了一个可计算的三维关键点结构。系统后续不是在屏幕上机械盖图，而是根据这些关键点重建一个实时变化的脸部网格，再把川剧脸谱纹理映射到这个网格上。

## 5. MediaPipe Hands 的作用

Hands 输出每只手 21 个三维关键点，包括手腕、手掌节点、五根手指的各个关节和指尖。

项目中 Hands 的作用包括：

1. 判断手是否进入脸部区域。
2. 判断手是张开还是握拳。
3. 判断手掌或指尖是否拂过面部。
4. 判断是否形成遮脸动作。
5. 为舞扇遮脸提供手腕和拳头位置。
6. 为侧首吐火提供同侧手部抬起位置。
7. 为手部遮挡 overlay 提供几何范围。

项目当前并没有直接训练一个端到端视频动作识别模型，而是把 Hands 的关键点结果作为输入，通过规则状态机和时序逻辑识别动作。这个设计是合理的，因为当前动作类别明确、样本量有限、现场演示要求低延迟、可解释性要求高。

## 6. 动作识别技术路线

项目的动作识别不是简单点击按钮，也不是只看单帧姿态。它是基于关键点的时序状态机。

状态机主要利用以下信息：

1. 手部关键点与脸部区域的位置关系。
2. 手部轨迹在连续帧中的移动方向和速度。
3. 手部是否进入、穿过或覆盖面部核心区域。
4. 头部 yaw 是否离开正面并回到正面。
5. 手部形态是否接近握拳或张手。
6. 当前是否处于冷却帧。
7. 触发后是否需要重置状态。

### 6.1 纵向挥手变脸

纵向挥手主要模拟“手从脸前拂过”的变脸动作。系统先根据 FaceMesh 得到面部区域，再根据 Hands 得到手部位置。如果手部关键点进入面部区域，并在连续帧中形成明显的纵向位移，同时满足速度、方向和区域交叠条件，就触发换脸。

这个逻辑比“看到手就换脸”更稳。因为真实用户可能会摸头、整理头发、从脸旁经过或把手停在脸边，如果不判断轨迹和冷却，很容易误触发。

### 6.2 转头回正变脸

转头变脸采用“侧转 -> 回正 -> 触发”的逻辑。

系统持续估计头部 yaw 角。当 yaw 超过侧转阈值时，状态机记录用户已经转向某一侧；当 yaw 回到接近正面的阈值范围内，并且侧转峰值达到要求时，才触发脸谱切换。

这个设计对应川剧表演中的舞台逻辑：演员不是刚转头就变脸，而是通过转身、遮挡、回身完成瞬间换容。技术上，这可以降低误触发，因为用户只是短暂看旁边不会立刻换脸。

### 6.3 舞扇遮脸变脸

舞扇遮脸使用手部或拳头位置模拟扇子动作。系统判断手腕、拳头与脸部区域的位置关系，并计算扇面覆盖脸部的比例。当遮挡稳定持续若干帧后，才触发换脸。

这个功能的核心不是“识别真正的扇子材质”，而是基于手部姿态和扇子图像叠加实现舞台效果。当前是前端交互特效，不是通用物体检测。

### 6.4 侧首吐火

吐火效果结合头部侧转方向和同侧手部抬起。系统判断 yaw 是否达到侧转阈值，再判断对应方向的手是否抬到合适区域，满足后进入火焰状态机。火焰通过 canvas 粒子绘制，不是后端生成视频。

吐火状态通常包括 idle、charging、firing、cooldown 等阶段。这样可以让特效更像一个动作过程，而不是瞬间闪一下。

## 7. 冷却帧、防抖和平滑机制

实时摄像头通常每秒 25 到 30 帧。如果没有冷却机制，一个挥手动作会在多帧中连续满足触发条件，导致一次动作换多张脸。

项目使用冷却帧解决这个问题。一次触发后，系统在若干帧内拒绝新的换脸触发，把连续的帧级检测结果压缩成一次语义动作。

项目还使用关键点平滑来减少抖动。摄像头画面中的关键点会受到光照、遮挡、模型置信度和用户微动影响。如果直接用原始关键点，脸谱边缘会跳动。平滑机制会将当前帧关键点与上一帧结果加权融合，类似 EMA 的思想。

这里需要注意一个答辩点：

平滑越强，画面越稳，但延迟越高；平滑越弱，响应越快，但抖动越明显。项目选择的是面向实时舞台的折中策略，目标是让脸谱稳定跟脸，同时不明显拖延。

## 8. Three.js 实时脸谱渲染

实时脸谱渲染由 Three.js 实现。项目维护一个 Three.js scene、camera、renderer 和人脸 mesh。

核心流程为：

1. 初始化 Three.js 渲染环境。
2. 创建人脸网格。
3. 加载脸谱 PNG 作为 texture。
4. 将 texture 绑定到 mesh material。
5. 每帧用 FaceMesh 关键点更新 mesh 顶点。
6. 根据姿态更新位置、缩放和旋转。
7. 渲染到覆盖在摄像头上的 canvas。

和普通二维贴纸相比，这种方式的优势是：

1. 能适应脸部缩放。
2. 能跟随转头。
3. 能体现脸部轮廓和五官区域。
4. 能与 Three.js 后续三维资产展示衔接。

当前实时舞台中，系统故意关闭了实时个人 OBJ 驱动，使用标准面部网格。这是工程取舍：实时舞台优先稳定，个人 OBJ 更适合在三维模型页展示。

## 9. 实时舞台为什么不用个人 OBJ

这是答辩时非常重要的问题。

个人 OBJ 适合展示，但不适合直接用于实时舞台每帧驱动。原因包括：

1. 个人 OBJ 的顶点拓扑可能与 MediaPipe 468 点不一致。
2. OBJ 顶点数量、UV 布局和关键点映射需要额外绑定。
3. 实时更新复杂 OBJ 顶点会增加计算开销。
4. 如果绑定不准，转头时更容易穿模、撕裂和露出未贴图区域。
5. 用户体验中实时变脸稳定性比模型复杂度更重要。

因此项目采用分层策略：

- 实时舞台：标准面部网格 + 关键点驱动 + 预制脸谱纹理。
- 个人模型页：OBJ/GLB + UV 贴图 + OrbitControls 360 度查看。

这不是功能缺失，而是工程设计：将“实时交互”和“三维资产展示”分开，避免互相拖累。

## 10. 背面露白和穿模问题的技术原因

之前出现过转头时露出白色未贴图部分，这类问题通常来自：

1. 模型背面或内侧材质没有贴图。
2. 转头时显示了不应显示的 back mesh。
3. material side 设置不合适。
4. alpha 区域或 UV 边界处理不完整。
5. 手部遮挡层与脸谱层级关系不正确。

当前实时舞台的修复策略是：

1. 不在实时舞台显示白色背面 mesh。
2. 使用双面材质减少转头时单面剔除问题。
3. 对贴图 alpha 做基本阈值处理。
4. 把内侧素面材质限制在个人三维模型展示页，而不是实时变脸舞台。

答辩中可以说：

实时舞台和三维模型展示对“内侧材质”的要求不同。舞台中用户主要看正面变脸效果，所以必须避免内侧露出破坏体验；三维模型页中用户可以旋转查看，所以内侧素面是合理的展示设计。

## 11. 手部遮挡是如何实现的

真实世界中，手在脸前时应该遮住脸谱。如果只是把脸谱渲染在视频上方，脸谱会压住手，显得非常假。

当前项目使用的是前端关键点遮挡 overlay：

1. Hands 检测手部关键点。
2. 根据手掌、指尖等点估算手部区域。
3. 从原始视频画面中取出手部区域。
4. 在脸谱层上方绘制这部分手部图像。
5. 形成手遮住脸谱的视觉关系。

这不是 SAM 像素级分割，但对实时浏览器体验更轻量。它的优势是速度快、无需 GPU、无需外部模型。局限是边界不如真实分割精细，快速运动和复杂手势下会有误差。

SAM 在项目中的定位是后续增强接口，而不是当前实时主路径。

## 12. 脸谱纹理与 UV 贴图基础

UV 贴图是三维模型表面与二维图片之间的坐标对应关系。三维模型顶点有 x、y、z 坐标，同时也可以有 u、v 坐标。u、v 指向二维贴图上的位置。

简单说：

三维脸谱面罩是一个立体表面，脸谱 PNG 是一张平面图。UV 贴图就是告诉系统：这张平面图上的眼睛、鼻子、嘴巴、脸颊纹样，应该贴到三维模型的哪些位置。

项目中有两类贴图：

1. 实时舞台贴图：偏向实时稳定和视觉对齐。
2. 后端生成 UV 贴图：偏向个人三维面罩资产的可展示性。

## 13. 自动贴图是如何实现的

项目中的“自动贴图”要精确描述，不能说成完全无需人工的自动语义贴图。

当前真实实现是：

1. 每张脸谱 PNG 有对应的角色 key。
2. 系统根据 textureKey 找到脸谱图片。
3. 系统根据 textureKey 找到锚点 JSON。
4. 如果找不到专属锚点，会使用默认锚点兜底。
5. 后端读取标准 UV 模板和模板锚点。
6. `generate_face_uv.py` 使用锚点做 piecewise affine warping。
7. 输出标准 UV 空间下的 PNG。
8. 该 UV PNG 后续绑定到 OBJ/GLB 材质中。

这个过程的关键是锚点。

当前脚本要求的锚点包括：

- left_eye
- right_eye
- nose_tip
- mouth_left
- mouth_right
- chin
- forehead
- left_cheek
- right_cheek

脚本会把原始脸谱图中的这些锚点映射到标准 UV 模板中的对应锚点，然后用 Delaunay 三角剖分把脸谱图切成多个三角区域。每个三角区域做仿射变换，最后 alpha blend 到输出 UV 图中。

这个技术叫 piecewise affine warping，分片仿射变形。它比简单缩放和平移更强，因为不同面部区域可以局部变形，从而让眼睛、鼻子、嘴部和脸颊更接近模板位置。

## 14. 自动贴图的真实边界

真正实现的是：

1. 根据 textureKey 自动选择脸谱 PNG。
2. 根据 textureKey 自动选择 anchors JSON。
3. 自动调用 UV 生成脚本。
4. 自动做 Delaunay 三角剖分。
5. 自动做分片仿射变形。
6. 自动输出 UV PNG。
7. 自动进入后续 GLB 导出流程。

不能夸大的是：

1. 锚点不是对每张新脸谱完全自动识别出来的。
2. 如果新脸谱没有准确 anchors，自动贴图质量会下降。
3. 当前不是基于深度语义分割自动理解所有纹样。
4. 当前不是每个脸型都自动学习最优 UV。

答辩中最稳的说法是：

项目已经实现“基于语义锚点的自动 UV 烘焙流程”。当脸谱图和锚点数据准备好后，系统可以自动把二维脸谱变换到标准 UV 空间并绑定到三维面罩；但锚点数据仍属于内容制作资产，不宜宣传为完全无人工的新脸谱自动解析。

## 15. 3DDFA-V3 在项目中具体怎么用

3DDFA-V3 是项目后端三维脸型拟合的真实 provider 之一。它的作用不是实时舞台贴脸，而是为个人三维脸谱面罩生成提供 OBJ 几何基础。

项目后端的 3DDFA-V3 使用流程为：

1. 前端从摄像头采集一组人脸图像。
2. 前端同时发送 fallback OBJ 文本，作为保底输入。
3. 后端先做多视角质量筛选。
4. 如果 3DDFA-V3 资源完整且有可用图像，选择 `3ddfa-v3` provider。
5. 后端调用 `3DDFA-V3/export_obj_adapter.py` 或 `demo.py`。
6. 调用参数包括输入图片、输出目录、device、detector、backbone。
7. 3DDFA-V3 输出 OBJ。
8. 后端复制或融合 OBJ 到任务输出路径。
9. 后续进行 UV 生成、法线图生成和 GLB 导出。

实际代码中，provider 选择逻辑是：

- `auto` 模式下，如果有图像输入并且 3DDFA-V3 资产完整，走 `3ddfa-v3`。
- 如果无法走 3DDFA-V3，但前端传了 fallback OBJ，走 `fallback-obj`。
- 如果连 fallback OBJ 都不可用，走 `mock`。

## 16. 多视角 3DDFA-V3 是如何处理的

如果只有一张人脸图像，后端直接调用一次 3DDFA-V3。

如果有多张入选图像，后端会对每张图分别调用 3DDFA-V3，生成多个 OBJ。然后假设这些 OBJ 拥有相同拓扑，读取每个 OBJ 的顶点坐标，对顶点位置进行融合，写回一个新的 OBJ。

这类融合属于工程化近似，优点是可以利用多个角度的信息，让结果比单帧更稳；限制是它依赖同拓扑输出，不等同于完整的多视角神经重建。

答辩中可以这样说：

项目使用多视角短 burst 采集和质量筛选增强输入稳定性，在后端用同拓扑 OBJ 顶点融合形成个人脸型结果。它是面向展示资产的工程化三维面罩生成，不是电影级高保真人脸扫描。

## 17. 3DDFA-V3 的真实边界

真正实现的是：

1. 后端已经有 3DDFA-V3 调用逻辑。
2. 后端会检查必要资产是否存在。
3. 支持 CPU 或 CUDA device 参数。
4. 支持 retinaface detector 和 backbone 参数。
5. 支持单图和多图调用。
6. 支持 fallback 到前端 OBJ 或 mock。

不能夸大的是：

1. 无 GPU 电脑上 3DDFA-V3 可能很慢。
2. 如果依赖、模型权重或图片质量不满足条件，会降级。
3. 当前不应称为“高保真人脸重建”。
4. 当前不保证身份级精确复刻。
5. 当前不用于实时舞台逐帧变脸。

最准确的名称是：个性化三维脸谱面罩生成。

## 18. 多视角质量筛选

项目不是盲目使用摄像头第一帧，而是对短 burst 采集帧进行筛选。后端会记录每帧的清晰度、曝光、对比度、分辨率、前端质量分和姿态 bucket。

评分考虑：

1. sharpnessScore
2. exposureScore
3. contrastScore
4. resolutionScore
5. frontendQualityScore
6. yaw 姿态覆盖

输出 `capture_manifest.json`，记录：

1. 输入帧数量。
2. 入选帧数量。
3. 每帧质量分。
4. 姿态覆盖。
5. 生成路线。

这个 manifest 很重要，因为它让三维生成过程可解释。答辩时可以说：

我们不是黑盒生成一个模型，而是记录采集、筛选、重建、贴图、导出的全过程，便于展示和排查。

## 19. OBJ、GLB、normal map 与 manifest

后端生成任务通常输出：

- `personal_face.obj`
- `{textureKey}_mask.glb`
- `{textureKey}_detail_normal.png`
- `{textureKey}_asset_manifest.json`

OBJ 是中间几何资产，便于调试和兼容。GLB 是更适合 Web 展示的二进制三维格式，可以封装几何、材质和贴图。normal map 是从脸谱贴图亮度中生成的细节法线图，用于增强材质层次。asset manifest 记录生成来源、profile、provider、capture 信息、OBJ/GLB/normal map 路径。

这里可以强调：

manifest 是项目工程化的重要证据，说明生成链路不是前端静态图假装，而是真实存在任务状态、输出文件和元数据记录。

## 20. Blender 与 trimesh 的分工

GLB 导出有两条路线：

1. Blender 路线。
2. Python/trimesh 路线。

Blender 路线质量更高，可以更好处理材质、贴图、法线图和导出设置。trimesh 路线是兜底方案，适合没有 Blender 时保证能生成一个可用 GLB，但材质表现弱一些。

答辩时可以说：

项目采用优先高质量、失败可降级的工程策略。能找到 Blender 就用 Blender 导出更完整的 GLB；找不到 Blender 时，用 trimesh 保证流程不断。

## 21. 后端任务系统

后端使用 FastAPI 提供接口，三维生成任务不是同步阻塞页面，而是异步 job 模式。

流程为：

1. 前端提交生成任务。
2. 后端创建 jobId。
3. 后端进入后台线程或任务流程。
4. 前端轮询 job 状态。
5. job 状态更新为采集、筛选、重建、UV、GLB、完成或失败。
6. 完成后返回 OBJ、GLB、manifest 等 URL。

项目还限制最大并发任务数，防止普通电脑同时跑多个重型任务崩溃。这是合理的，因为个人电脑 CPU 模式下重建资源有限。

## 22. 个人三维模型展示页

个人模型页读取以下来源：

1. URL 参数中的 OBJ、texture、manifest。
2. sessionStorage 中的生成 payload。
3. localStorage 中的已体验脸谱记录。
4. 默认样例 OBJ。

页面用 Three.js 解析 OBJ，构建 geometry，加载脸谱 texture，并用 OrbitControls 允许用户旋转查看。外侧显示脸谱纹理，内侧保持素面材质。这符合真实面罩逻辑：脸谱画在外侧，内侧不应继续贴脸谱图案。

真实实现的是：可旋转查看三维脸谱面罩。  
不宜夸大的是：这不是完整的人脸身份级数字孪生。

## 23. 脸谱收藏馆技术路线

收藏馆用弧形 carousel 展示脸谱。它读取角色库和体验记录，中心脸谱高亮，两侧脸谱弱化。用户滚动或切换时，更新当前角色、剧目、唱段和视频候选。

收藏馆承担的是“文化内容组织”功能，而不是单纯图片展示。

它把以下内容连起来：

1. faceKey
2. 角色名
3. 谱式
4. 颜色
5. 寓意
6. 剧目
7. 唱段 mp3
8. 视频检索入口
9. 已体验脸谱记录
10. 个人三维模型入口

这使得用户的体验不是一次性特效，而是可以进入角色语境。

## 24. 唱段联动实现边界

项目已经实现唱段映射机制。每个脸谱绑定一个剧目 slug，系统根据 slug 查找本地 mp3。已存在的 mp3 会自动接入并播放。

真正实现的是：

1. 有本地唱段目录。
2. 有 faceKey -> 剧目 -> slug -> mp3 URL 映射。
3. 收藏馆切换脸谱时可以切换音频源。
4. 用户点击播放后，后续切换可继续播放对应唱段。

不宜夸大的是：

1. 并非所有 12 个角色都已有真实 mp3。
2. 缺失唱段不能说成已经完整接入。
3. 外部检索入口不是内置版权视频库。

最稳说法：

项目已实现按脸谱切换唱段的技术机制，并接入部分本地经典唱段资源；未补齐角色仍需要继续整理合法音频素材。

## 25. 剧目视频检索实现边界

项目为每个角色生成视频和资料检索候选，包括川剧发展研究中心、梨园戏考、公开视频平台和综合搜索。

真正实现的是：

1. 根据当前剧目生成外部链接。
2. 用户点击可以跳转对应站点或搜索结果。
3. 视频检索与当前脸谱角色相关联。

不宜夸大的是：

1. 项目没有内置完整正版川剧视频库。
2. 专业站点不一定提供直接播放视频。
3. 外部搜索结果的准确性取决于平台内容。

## 26. 小谱 AI Agent 技术路线

小谱是项目的 AI 导览层。它不是纯固定脚本，也不是完全自由聊天。

流程为：

1. 前端获取用户问题。
2. 前端收集当前页面上下文，例如当前脸谱、页面模式、收藏数量。
3. 请求 FastAPI `/api/ai/agent`。
4. 后端检索 RAG 文档。
5. 后端调用工具：文化图谱、推荐、媒体资源、系统状态等。
6. 如果 DeepSeek API 配置可用，使用 DeepSeek 生成回答。
7. 如果 DeepSeek 不可用，使用本地 RAG fallback。
8. 返回前清洗回答格式。
9. 前端显示在小谱对话框中。

小谱的关键不是“会聊天”，而是能结合当前脸谱和项目知识回答。

## 27. RAG 的真实实现

项目中的 RAG 是本地轻量检索，不是大型向量数据库。

知识库由多类文档组成：

1. 角色知识文档。
2. 颜色寓意文档。
3. 项目技术文档。
4. 外部资料摘要。
5. RAG、Agent、MediaPipe、3DDFA 等技术说明。

检索方式是 token 匹配和加权打分。标题命中权重更高，标签命中次之，正文命中再次之；如果传入 currentFaceKey，会额外提升当前脸谱相关文档分数。

真正实现的是：

1. 本地文档构建。
2. query token 化。
3. 标题、标签、正文加权检索。
4. 当前脸谱加权。
5. 返回带 score 的文档片段。
6. DeepSeek 回答时把 RAG context 放进 prompt。

不宜夸大的是：

1. 当前不是向量数据库。
2. 当前没有 embedding 相似度检索。
3. 当前没有复杂 reranker。
4. 当前不是企业级知识图谱问答系统。

但对项目答辩来说，这个 RAG 是真实有效的轻量实现。

## 28. GraphRAG 与文化关系图

项目还实现了轻量文化图谱。节点包括角色、颜色、寓意和剧目。边表示角色与颜色、颜色与寓意、角色与剧目之间的关系。

GraphRAG 的作用是：

1. 让文化知识不只是文本堆叠。
2. 支持从角色追溯颜色和寓意。
3. 支持从剧目追溯相关角色。
4. 支持小谱进行关系解释。
5. 支持推荐下一张脸谱。

真实实现的是轻量图结构和图搜索。  
不宜夸大为大型工业知识图谱平台。

## 29. 推荐算法边界

项目中的推荐使用 contextual bandit 风格的轻量打分，不是深度推荐系统。

它考虑：

1. 当前脸谱。
2. 用户看过哪些脸谱。
3. 偏好事件。
4. 颜色、寓意、剧目差异。
5. 角色之间的文化连贯性。

真实实现的是：基于上下文和偏好事件的轻量推荐。  
不宜夸大的是：这不是经过大规模用户行为训练的商业推荐模型。

## 30. VLM 视觉质检

视觉质检接口可以接外部 VLM 服务。如果没有配置外部服务，项目使用本地 fallback。

本地 fallback 主要检查：

1. 画面亮度。
2. 对比度。
3. 清晰度。
4. 调色板。
5. 人脸关键点是否存在。
6. 手脸遮挡比例。

真实实现的是：本地图像统计 + 关键点质量规则。  
预留的是：外部 VLM 对画面进行更高级语义分析。  
不宜说成：本机已经完整跑了大视觉语言模型。

## 31. CLIP 多模态检索

CLIP 接口同样是可插拔设计。配置外部服务时，可以调用真正的 CLIP 类模型；未配置时，本地 fallback 使用颜色直方图和文本语义规则做近似检索。

本地 fallback 的逻辑包括：

1. 读取当前图像。
2. 计算颜色直方图。
3. 读取脸谱库图片。
4. 比较颜色分布。
5. 根据 query 中的角色、颜色、寓意关键词加分。
6. 返回相似脸谱排序。

真实实现的是轻量多模态近似检索。  
不宜夸大为完整 CLIP 模型在本机推理。

## 32. SAM 遮挡分割

SAM 接口可以接外部 SAM2 服务。未配置时，本地 fallback 使用手部关键点构造凸包或扩展多边形，估算遮挡区域。

真实实现的是：

1. 读取手部 landmarks。
2. 构造手部 polygon。
3. 与人脸 bbox 计算重叠。
4. 返回遮挡区域、比例和质量信息。

预留的是：

1. 外部 SAM/SAM2 像素级分割。
2. 更精细的手指边界。
3. 扇子与脸谱边缘的语义遮挡。

答辩时不能说实时舞台已经完全依赖 SAM。准确说法是：实时主路径使用关键点遮挡，SAM 是可插拔增强接口。

## 33. AI 创作脸谱

AI 创作脸谱接口可以基于 DeepSeek 生成设计说明，也可以在本地 fallback 中根据当前脸谱和提示生成结构化设计 spec，再输出可编辑 SVG。

真实实现的是：

1. 根据 prompt 和当前脸谱生成 palette、寓意、线条描述。
2. 可调用 DeepSeek 优化设计结构。
3. 输出 editableSvg。

不宜夸大的是：

1. 当前不是专业图像生成模型直接生成高质量位图脸谱。
2. 当前更接近结构化脸谱设计草图和 SVG 生成。

## 34. 3DGS 当前状态

项目保留了 3DGS 相关后端接口和 manifest 管理逻辑，但当前主流程不是本机训练 3D Gaussian Splatting。

真实实现的是：

1. 3DGS 状态接口。
2. 场景 manifest 管理。
3. 外部训练服务配置入口。
4. 本机无 GPU 时的说明和管理逻辑。

不宜夸大的是：

1. 当前本机没有完整训练 3DGS。
2. 当前用户主页面已不突出 3DGS。
3. 经典川剧场景 3DGS 需要你后续提供视频、唱段和训练资产。

最稳说法：

3DGS 是项目的沉浸式扩展方向，当前保留接口和资产管理路线，真实训练建议放到 AutoDL CUDA 环境完成。

## 35. 手势训练与 AutoDL 路线

项目内有手势采集面板和训练脚本。采集的数据主要是关键点序列，不是原始视频。

训练路线为：

1. 本地舞台采集动作样本。
2. 导出 JSON。
3. 上传 AutoDL。
4. 运行数据校验脚本。
5. 训练 TCN/LSTM/1D-CNN 等轻量时序模型。
6. 导出权重。
7. 下载回本地项目推理。

真实实现的是：

1. 本地关键点采集和导出工具。
2. 数据校验脚本。
3. TCN 训练脚本。

不宜夸大的是：

1. 当前普通用户主流程不依赖训练。
2. 当前训练后模型是否已经完整接入实时舞台，需要根据后续实际集成情况说明。
3. 没有足够样本时，不应声称模型泛化很强。

## 36. 性能与 CPU 模式

你的个人电脑没有 GPU，因此项目采用 CPU 可运行策略。

CPU 模式设置包括：

1. `HQ_MASK_MODE=real`
2. `HQ_MASK_FACE_PROVIDER=auto`
3. `DDFA_V3_DEVICE=cpu`
4. `HQ_MASK_MAX_ACTIVE_JOBS=1`
5. `HQ_MASK_GLB_EXPORTER=auto`

前端实时舞台主要依赖浏览器和 MediaPipe wasm，通常比后端 3D 重建更适合 CPU 演示。后端 3DDFA-V3 如果能跑，会比较慢；如果不适合当前环境，就 fallback 到前端 OBJ 或 mock。

答辩中可以说：

项目针对无 GPU 环境做了分层降级：实时交互继续运行，AI 问答走 API，本地三维生成优先尝试真实重建，失败时保留展示链路。

## 37. 安全性与隐私边界

项目的安全设计包括：

1. DeepSeek API key 由后端环境变量或 `.env` 读取，不应写入前端代码。
2. 前端不直接调用 DeepSeek，避免泄露 key。
3. 摄像头实时变脸主要在浏览器端处理。
4. 只有执行三维生成时才会上传必要人脸帧到本地后端。
5. 小谱回答基于 RAG 上下文和工具结果，减少自由编造。

仍可加强的地方：

1. 上传帧生命周期管理。
2. 用户隐私提示。
3. 本地缓存清理。
4. API 限流和鉴权。
5. 生成文件过期清理。

这些可以作为后续规划，但不应作为当前完成度宣传。

## 42. 答辩时最稳的总结口径

本项目的核心技术路线是：前端通过 MediaPipe 将摄像头中的人脸和手部动作转化为关键点序列，再用状态机和冷却帧识别川剧变脸中的挥手、遮脸、转头回正和吐火动作；渲染层使用 Three.js 将脸谱纹理实时映射到人脸网格，实现稳定的浏览器端变脸体验。后端使用 FastAPI 组织文化知识、RAG、小谱 Agent、唱段媒体和三维生成任务；三维生成链路支持多视角采集、质量筛选、3DDFA-V3 个人脸型拟合、锚点驱动 UV 烘焙、法线图和 GLB 导出，并在无 GPU 或依赖不足时自动降级到 fallback OBJ 或 mock，保证演示闭环不断。项目中真正成熟的是实时交互、脸谱收藏、小谱导览和三维面罩展示；SAM、CLIP、VLM 和 3DGS 是可插拔增强方向，当前已有接口和本地 fallback，但不应夸大为已完整本机实现。

## 43. 答辩时的核心底线

只要坚持这三句话，技术追问基本不会失控：

1. 实时舞台追求稳定，所以使用标准面部网格实时驱动，而不是把复杂个人 OBJ 强行逐帧绑定到脸上。
2. 三维生成追求可解释，所以保留 3DDFA-V3、fallback OBJ、mock、UV、GLB 和 manifest 的完整证据链。
3. AI 导览追求可信，所以用 RAG 和工具上下文约束小谱，而不是让大模型凭空讲川剧和项目技术。

项目最值得强调的不是某一个模型有多大，而是把实时视觉、三维渲染、文化知识、唱段媒体和 AI Agent 组织成了一个能演示、能解释、能降级、能继续扩展的非遗数字化系统。
